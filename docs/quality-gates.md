# Quality Gates для продукта склада

Документ задает минимальные ворота качества для перехода от MVP к полноценному production-продукту склада. Ворота применяются к каждому релизу, миграции схемы, изменению API и изменению бизнес-инвариантов.

## Цели

- Защитить складские остатки, партии, резервы и документы от неконсистентных изменений.
- Сделать релизы повторяемыми: один и тот же commit должен проходить одинаковый набор проверок в CI/CD.
- Обеспечить наблюдаемость, восстановление и аудит действий пользователей.
- Сохранять совместимость API для клиентов и интеграций.

## Gate 1. Тесты и бизнес-инварианты

**Критерии прохождения**

- Unit-тесты покрывают доменные правила: блокировка инвентаризации, FEFO, карантин/блокировка партий, резервы, списания, перемещения, возвраты, posting документов, дедупликация уведомлений.
- Интеграционные тесты проходят на PostgreSQL, а не только на SQLite.
- Проверены конкурентные сценарии: одновременное списание, резервирование, posting документа и инвентаризация одного склада.
- Для каждого исправленного дефекта добавлен regression-тест.
- Минимальное покрытие для бизнес-слоя и persistence-слоя фиксируется в CI. Рекомендуемый порог: не ниже 80% по строкам и 90% по критичным доменным веткам.

**Блокеры релиза**

- Любой падающий тест.
- Непокрытое изменение логики остатков, партий, резервов, audit log или posting документов.
- Флейки в критичных тестах, воспроизводимые чаще 1 раза на 20 прогонов.

## Gate 2. Security и доступы

**Критерии прохождения**

- Все mutating endpoints требуют аутентификацию через Keycloak/OAuth2 JWT.
- Роли и permissions проверяются на уровне route/service boundary: просмотр, приемка, списание, инвентаризация, approval, администрирование.
- Service-to-service доступы используют отдельные clients/scopes, а не пользовательские токены.
- Секреты хранятся вне репозитория: env, secret manager или Kubernetes secrets.
- Включены базовые security checks: dependency scan, secret scan, static analysis для небезопасных паттернов.
- Ошибки API не раскрывают stack trace, SQL, токены, персональные данные и внутренние идентификаторы с повышенным риском.

**Блокеры релиза**

- Endpoint, меняющий складские данные без авторизации или без проверки роли.
- Найденный secret в репозитории или образе.
- Critical/high vulnerability без принятого решения о mitigation.

## Gate 3. Audit и трассируемость действий

**Критерии прохождения**

- Все операции, меняющие остатки, документы, партии, настройки доступа и справочники, пишут append-only audit record.
- Audit record содержит: actor id, subject, operation, timestamp, correlation/request id, before/after или доменное событие, источник операции.
- Audit log не редактируется обычными сервисными операциями.
- Для фоновых задач audit содержит технического actor и ссылку на job id.
- Чтение audit log ограничено ролями, пагинацией и фильтрами по периоду/объекту.

**Блокеры релиза**

- Изменение баланса, партии, резерва или документа без audit record.
- Возможность штатно удалить или перезаписать audit record без отдельного административного процесса.

## Gate 4. Миграции базы данных

**Критерии прохождения**

- Все изменения схемы идут через Alembic migration.
- Миграция содержит `upgrade` и осознанный `downgrade` либо явную пометку, почему downgrade невозможен.
- Миграции прогоняются на пустой базе и на копии production-like данных.
- Backfill больших таблиц выполняется батчами и не блокирует запись дольше согласованного окна.
- Для breaking schema changes используется expand-contract подход: сначала добавить новое поле/таблицу, затем перевести код, затем удалить старое.
- Индексы для больших таблиц создаются с учетом lock-поведения PostgreSQL.

**Блокеры релиза**

- Ручное изменение схемы без миграции.
- Миграция, теряющая данные без отдельного утвержденного плана.
- Непроверенная миграция на production-like объеме.

## Gate 5. Совместимость API

**Критерии прохождения**

- OpenAPI schema генерируется и сравнивается с предыдущей стабильной версией.
- Breaking changes запрещены без версии API или согласованного migration window.
- Новые поля в response добавляются обратно совместимо.
- Удаление/переименование полей, изменение enum, изменение статусов ошибок и обязательности input-полей считается breaking change.
- Для интеграций фиксируются contract tests по ключевым сценариям: приемка, списание, резерв, инвентаризация, документы, audit read.
- Ошибки имеют стабильный формат: machine-readable code, human-readable message, details, correlation id.

**Блокеры релиза**

- Несогласованное breaking change в публичном API.
- Изменение бизнес-смысла существующего endpoint без обновления контрактов и документации.

## Gate 6. Performance и нагрузка

**Критерии прохождения**

- Есть baseline для критичных операций: чтение остатков, приемка, списание FEFO, резервирование, posting документа, инвентаризационный snapshot.
- P95 latency для пользовательских операций согласован и отслеживается. Рекомендуемый стартовый ориентир: P95 до 500 мс для обычных операций и до 2 с для тяжелых отчетных запросов.
- Нагрузочные тесты включают конкурентные записи по одной партии/складу.
- SQL-запросы критичных endpoints проверены на индексы и отсутствие N+1.
- Долгие отчеты, ABC/XYZ и генерация черновиков заказов выполняются фоновыми jobs.

**Блокеры релиза**

- Деградация P95/P99 больше согласованного порога без принятого решения.
- Запросы, блокирующие складские записи на длительное время.
- Отчетная нагрузка, влияющая на операции приемки, списания и резервирования.

## Gate 7. Backup и disaster recovery

**Критерии прохождения**

- Настроены регулярные PostgreSQL backups и point-in-time recovery, если это поддерживается инфраструктурой.
- S3/объектное хранилище имеет версионирование или lifecycle-политику для критичных вложений.
- Восстановление из backup проверяется по расписанию на отдельном окружении.
- Определены RPO и RTO. Рекомендуемый стартовый ориентир: RPO до 15 минут, RTO до 2 часов для складских операций.
- Runbook восстановления описывает владельца, шаги, проверки целостности и коммуникацию.

**Блокеры релиза**

- Backup настроен, но restore ни разу не проверен.
- Нет понимания, какие данные потеряются при отказе.
- Критичные файлы документов хранятся без резервирования.

## Gate 8. Monitoring и операционная готовность

**Критерии прохождения**

- Сервисы отдают health/readiness endpoints.
- Логи структурированы и содержат correlation id, actor id при наличии, operation, entity id, status.
- Метрики включают latency, error rate, DB pool, Redis connectivity, job queue depth, failed jobs, WebSocket connections, audit write failures.
- Настроены алерты для: недоступности API, роста 5xx, ошибок миграций, ошибок audit write, отставания фоновых задач, проблем backup, заполнения диска.
- Есть dashboards для API, PostgreSQL, Redis, background jobs и бизнес-операций склада.
- Для релиза есть smoke checklist: login, справочники, приемка, списание, резерв, inventory lock, audit log, WebSocket event.

**Блокеры релиза**

- Production-релиз без health/readiness checks.
- Ошибки audit write или posting документов не алертятся.
- Нет видимости состояния очередей и фоновых задач.

## Gate 9. Data quality и консистентность остатков

**Критерии прохождения**

- Регулярная проверка сверяет партии, движения, резервы и агрегированные остатки.
- Отрицательный свободный остаток невозможен на уровне service logic и защищен транзакциями/constraints там, где применимо.
- Для документов posting идемпотентен: повторный запрос не создает повторное движение.
- Статусы партий и документов меняются только допустимыми state transitions.
- Для критичных справочников есть уникальность, нормализация и soft-delete/архивация вместо физического удаления, если объект уже участвовал в движениях.

**Блокеры релиза**

- Возможность получить отрицательный свободный остаток штатным API.
- Несовпадение агрегированных остатков и movement ledger без плана исправления.
- Повторный posting документа создает дублирующие движения.

## Gate 10. Release readiness

Перед production rollout владелец релиза подтверждает:

- CI зеленый на тестах, линтинге, security scan и миграциях.
- Миграции применены на staging и проверены на production-like данных.
- OpenAPI diff проверен.
- Нагрузочный baseline не ухудшен сверх согласованного порога.
- Backup/restore проверка актуальна.
- Dashboards и alerts готовы.
- Rollback/roll-forward план описан.
- Smoke checklist выполнен после деплоя.

Релиз считается непригодным к production, если хотя бы один блокер из gates выше остается открытым без явного risk acceptance от владельца продукта и технического лидера.
