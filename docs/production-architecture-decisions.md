# Production Architecture Decisions

Документ фиксирует целевые архитектурные решения для production-версии складского продукта. Формат близок к ADR: контекст, решение, последствия и практические правила внедрения.

## ADR-001. PostgreSQL как основная база данных

**Статус:** принято для production.

**Контекст**

MVP может использовать SQLite для локальной разработки и быстрых тестов, но production-склад требует транзакционной надежности, конкурентных записей, блокировок, индексов, резервного копирования и восстановления.

**Решение**

Использовать PostgreSQL как единственный production storage для остатков, партий, документов, движений, резервов, пользователей доменной модели, audit log и outbox-событий.

**Практические правила**

- Все операции, меняющие остатки, выполняются в транзакциях.
- Конкурентные изменения одной партии/резерва защищаются row-level locking или атомарными условными update.
- Движения склада хранятся как ledger; агрегаты остатков могут быть материализованы, но должны сверяться с ledger.
- Внешние ключи, уникальные ограничения и индексы отражают доменные инварианты.
- Для audit log и movement ledger не используется физическое удаление штатными пользовательскими операциями.

**Последствия**

- Появляется инфраструктурная зависимость от PostgreSQL и DBA-практик.
- Интеграционные тесты должны запускаться на PostgreSQL.
- Нужны backup, PITR, мониторинг locks, slow queries и capacity planning.

## ADR-002. Alembic для версионирования схемы

**Статус:** принято для production.

**Контекст**

Складская схема будет развиваться: документы, approvals, интеграции, audit, аналитика, WebSocket outbox. Ручные изменения схемы создают риск рассинхронизации окружений.

**Решение**

Все изменения схемы БД выполняются через Alembic migrations, хранятся в репозитории и применяются CI/CD pipeline.

**Практические правила**

- Одна миграция решает одну понятную задачу.
- Миграции проверяются на чистой базе и на копии production-like данных.
- Для больших таблиц backfill выполняется отдельно или батчами.
- Breaking schema changes проходят через expand-contract.
- Downgrade описывается явно; если он невозможен, это фиксируется в комментарии миграции и release plan.

**Последствия**

- Релизы требуют дисциплины вокруг порядка применения миграций и кода.
- Нужна автоматическая проверка head revisions, конфликтующих branches и повторного применения миграций.

## ADR-003. SQLAlchemy как persistence layer

**Статус:** принято для production.

**Контекст**

Нужен явный слой доступа к данным, который поддерживает PostgreSQL, транзакции, eager loading, typed models и контроль SQL-запросов.

**Решение**

Использовать SQLAlchemy для ORM/Core persistence, отделяя доменную логику от деталей БД.

**Практические правила**

- Service layer управляет транзакционной границей бизнес-операции.
- Repository/persistence layer инкапсулирует SQL-запросы и locking strategy.
- Не смешивать HTTP request models и ORM models.
- Для критичных операций разрешен SQLAlchemy Core или raw SQL, если ORM мешает выразить атомарность или производительность.
- N+1 проверяется тестами или профилированием для списков и отчетов.

**Последствия**

- Требуется единый стиль сессий и транзакций.
- Разработчики должны понимать lazy/eager loading и влияние ORM на SQL.

## ADR-004. Redis для pub/sub, cache и координации

**Статус:** принято с ограниченным scope.

**Контекст**

Production-система нуждается в доставке событий WebSocket-подписчикам, быстрых ephemeral-состояниях и координации фоновых задач. Redis удобен для этих задач, но не должен становиться источником истины по складским данным.

**Решение**

Использовать Redis для pub/sub, transient cache, distributed locks при необходимости и технических очередей, если выбранный worker stack это поддерживает. Источник истины остается в PostgreSQL.

**Практические правила**

- Остатки, партии, документы и audit не хранятся только в Redis.
- Cache invalidation привязан к committed domain events.
- Distributed locks имеют TTL и не заменяют транзакционные гарантии PostgreSQL.
- Отказ Redis не должен повреждать данные; максимум допустима временная деградация realtime/cache/job processing.

**Последствия**

- Нужен мониторинг Redis latency, memory, evictions, reconnects.
- Нужно проектировать деградацию WebSocket и фоновых задач при недоступности Redis.

## ADR-005. Background jobs для отложенной и тяжелой работы

**Статус:** принято для production.

**Контекст**

Часть задач не должна выполняться в HTTP request path: истечение резервов, уведомления о сроках годности, ABC/XYZ анализ, генерация черновиков заказов, отправка интеграционных событий.

**Решение**

Выделить background worker process и scheduler. HTTP API только фиксирует транзакционное изменение и, при необходимости, создает job/outbox record.

**Практические правила**

- Jobs идемпотентны и безопасны к повторному запуску.
- Для задач, завязанных на данные БД, предпочтителен transactional outbox в PostgreSQL.
- Каждая job пишет статус, попытки, ошибку, timestamps и audit при изменении доменных данных.
- Долгие jobs имеют batch size, timeout и retry policy.
- Scheduler не должен запускать несколько конфликтующих экземпляров одной задачи без lock/lease механизма.

**Последствия**

- Появляется отдельная операционная поверхность: очереди, retries, dead letters, dashboards.
- Нужно явно тестировать поведение при повторном запуске и частичных отказах.

## ADR-006. Keycloak для identity и access management

**Статус:** принято для production.

**Контекст**

Складская система требует управляемой аутентификации, ролей, интеграций с корпоративной учетной записью и централизованного lifecycle пользователей.

**Решение**

Использовать Keycloak как OAuth2/OIDC provider. Backend проверяет JWT, issuer, audience, expiry, scopes/roles и применяет route-level и service-level RBAC.

**Практические правила**

- Backend не хранит пароли пользователей.
- Роли Keycloak маппятся в доменные permissions.
- Административные операции требуют отдельных ролей.
- Service accounts используются для интеграций и фоновых сервисов.
- Для audit сохраняется стабильный actor id из токена и отображаемые данные на момент операции, если это требуется регуляторно.

**Последствия**

- Локальная разработка требует dev realm или mock identity provider.
- Нужно версионировать настройки realm/client или управлять ими через инфраструктурный код.

## ADR-007. S3-совместимое хранилище для файлов

**Статус:** принято для production.

**Контекст**

Складские документы могут иметь вложения: сканы накладных, акты инвентаризации, файлы интеграций, печатные формы. База данных не должна хранить крупные бинарные объекты.

**Решение**

Использовать S3-совместимое объектное хранилище для файлов, а в PostgreSQL хранить metadata, ownership, checksum, content type, size и ссылку на object key.

**Практические правила**

- Object keys не содержат пользовательских секретов и персональных данных.
- Доступ к файлам идет через backend или short-lived signed URLs.
- Загрузка файла и создание metadata согласуются через transactional pattern: pending metadata, upload, finalize.
- Для критичных документов включаются versioning/lifecycle/retention политики.
- Проверяется content type, размер и checksum.

**Последствия**

- Нужно обрабатывать orphan objects и metadata без файла.
- Backup-стратегия должна покрывать и PostgreSQL, и объектное хранилище.

## ADR-008. WebSocket events для realtime-обновлений

**Статус:** принято для realtime-интерфейсов.

**Контекст**

Пользователям склада важно видеть изменения остатков, резервов, документов и уведомлений без ручного обновления страницы. При этом realtime не должен ломать транзакционную целостность.

**Решение**

Публиковать WebSocket events только после успешного commit бизнес-транзакции. Для надежности использовать outbox table в PostgreSQL и доставку через worker/Redis pub/sub к WebSocket nodes.

**Практические правила**

- Событие содержит event id, type, entity id, version/revision, timestamp и минимальный payload.
- Клиент должен уметь дозагружать актуальное состояние через REST API.
- WebSocket events являются сигналом об изменении, а не единственным источником данных.
- Доставка проектируется как at-least-once; клиенты должны выдерживать дубликаты.
- Права доступа проверяются при подписке и при доставке событий по warehouse/scope.

**Последствия**

- Нужна схема версионирования event types.
- Нужны метрики подключений, dropped events, lag outbox и reconnect rate.

## ADR-009. Modular monolith как основной стиль приложения

**Статус:** принято для ближайших production-инкрементов.

**Контекст**

Продукт склада включает связанные домены: справочники, остатки, партии, документы, инвентаризация, уведомления, audit, аналитика. Ранний переход к микросервисам увеличит сложность транзакций и эксплуатации.

**Решение**

Развивать систему как modular monolith: единый deployable backend с четкими внутренними модулями и границами владения. Внешние интеграции и фоновые workers могут быть отдельными процессами, но используют общий доменный контракт.

**Практические правила**

- Модули общаются через service interfaces, domain events или application services, а не через прямой доступ к чужим таблицам из произвольного места.
- Общие модели выносятся только при реальном повторном использовании.
- Доменная логика остается в service layer, а не в route handlers.
- Модульные границы фиксируются тестами и review checklist.
- Выделение отдельного сервиса возможно только после появления независимого lifecycle, нагрузки или команды владения.

**Последствия**

- Проще поддерживать транзакции и целостность остатков.
- Один релизный артефакт снижает операционную сложность.
- Требуется дисциплина, чтобы monolith не превратился в неструктурированный общий слой.

## Сквозные решения

### Транзакционная целостность

- Любая операция, меняющая складской баланс, должна быть атомарной.
- Posting документов идемпотентен.
- Ledger движений и audit пишутся в одной транзакции с доменным изменением или через надежный outbox-паттерн, если есть внешняя доставка.

### Event-driven boundaries

- Domain events создаются после принятого доменного решения.
- Integration/WebSocket events публикуются после commit.
- Дубликаты событий допустимы; потеря финального состояния недопустима, поэтому клиент и интеграции должны уметь сверяться через API.

### Наблюдаемость

- Каждый request/job получает correlation id.
- Ошибки домена имеют стабильные error codes.
- Метрики и логи должны позволять ответить: кто изменил остаток, почему изменился баланс, какая миграция применена, какая job отстала, какие клиенты не получили realtime-события.

### Production-путь внедрения

1. Перенести storage на PostgreSQL + SQLAlchemy.
2. Ввести Alembic и прогон миграций в CI.
3. Добавить Keycloak JWT verification и RBAC.
4. Добавить audit hardening и outbox table.
5. Подключить Redis и WebSocket delivery после commit.
6. Вынести scheduler/worker для reservation expiration, expiry notifications и аналитики.
7. Подключить S3 для файлов документов.
8. Закрыть quality gates по performance, backup, monitoring и API compatibility.
