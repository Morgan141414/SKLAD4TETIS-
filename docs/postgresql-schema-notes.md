# PostgreSQL Schema Notes

Практические рекомендации по production-схеме PostgreSQL для текущего склада. Документ дополняет `production-architecture-decisions.md` и `production-migration-plan.md`: здесь фокус на типах колонок, ограничениях, индексах, блокировках и миграции с SQLite.

## Базовые принципы

- PostgreSQL в production является единственным источником истины для остатков, партий, резервов, складских документов, движений, inventory sessions, audit log, outbox и idempotency.
- Все write-операции, которые меняют остатки или статусы документов, выполняются в одной транзакции на уровне application service / unit of work.
- Остатки должны быть защищены не только кодом, но и схемой: `NOT NULL`, `CHECK`, `UNIQUE`, `FOREIGN KEY`, индексы и транзакционные блокировки.
- Движения склада хранятся как ledger. Агрегированные остатки допустимы для скорости, но они должны быть проверяемы через ledger и корректироваться только контролируемыми операциями.
- Для доменных записей предпочтительно мягкое закрытие статуса вместо физического удаления. Физическое удаление допустимо для временных технических данных с явным retention policy.

## Типы данных

### Количества

Для складских количеств использовать `NUMERIC(18, 3)`.

Подходит для:

- `quantity`;
- `reserved_quantity`;
- `free_quantity`, если хранится материализованно;
- `movement_quantity`;
- `expected_quantity` и `actual_quantity` в инвентаризации;
- `min_stock`, `reorder_point`.

Правила:

- Не использовать `FLOAT`, `REAL`, `DOUBLE PRECISION` для количеств и денег.
- Для неделимых единиц все равно использовать `NUMERIC(18, 3)`, а кратность контролировать бизнес-правилом или `CHECK`, если единица измерения стабильна.
- Минимальный набор constraints:

```sql
CHECK (quantity >= 0),
CHECK (reserved_quantity >= 0),
CHECK (reserved_quantity <= quantity)
```

Для ledger-движений можно хранить знак в `direction`/`movement_type`, а `quantity` оставлять положительным:

```sql
CHECK (quantity > 0)
```

### Деньги и цены

Для цен выбрать один стандарт и закрепить его в первой production-миграции:

- `NUMERIC(18, 2)` для обычных денежных сумм в тенге/рублях/долларах;
- `NUMERIC(18, 4)` для закупочных цен, если нужны точные расчеты по мелким единицам и последующее округление в отчетах.

Практичнее для склада начать с `NUMERIC(18, 4)` для unit price и `NUMERIC(18, 2)` для итоговых сумм, если суммы вообще хранятся отдельно.

### Время

Для всех timestamps использовать `TIMESTAMP WITH TIME ZONE` (`timestamptz`).

Типовые поля:

- `created_at timestamptz NOT NULL DEFAULT now()`;
- `updated_at timestamptz NOT NULL DEFAULT now()`;
- `posted_at timestamptz`;
- `expires_at timestamptz`;
- `reserved_until timestamptz`;
- `published_at timestamptz`;
- `locked_at timestamptz`.

Правила:

- В API принимать и отдавать ISO 8601 со смещением или UTC.
- В базе не хранить локальное время без timezone.
- Для бизнес-дат без времени, например срок годности партии, использовать `DATE`, если время суток не имеет смысла.
- Для `updated_at` нужен единый механизм: application-level setter или PostgreSQL trigger. Не смешивать оба подхода без причины.

### JSONB

`jsonb` использовать для гибких технических payload, но не для основных доменных полей, по которым нужны связи, фильтры и constraints.

Хорошие кандидаты:

- `audit_log.diff_json`;
- `audit_log.request_context`;
- `outbox_events.payload`;
- `idempotency_keys.response_body`;
- metadata интеграционных событий;
- snapshot фактического request body для расследований, если это разрешено политикой хранения.

Правила:

- Важные поля payload дублировать в обычные колонки: `event_type`, `aggregate_type`, `aggregate_id`, `warehouse_id`, `actor_id`, `created_at`.
- Не хранить в `jsonb` секреты, токены, пароли, полные Authorization headers и лишние персональные данные.
- Для часто используемых jsonb-фильтров добавить expression index, но не начинать с широкого GIN на все подряд.

Пример:

```sql
CREATE INDEX ix_outbox_payload_document_id
ON outbox_events ((payload->>'document_id'));
```

## Ключи и идентификаторы

- Для внешних API и событий предпочтительны UUID: `uuid DEFAULT gen_random_uuid()`.
- Для внутренних surrogate keys допустимы `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Важно не смешивать смысловые номера документов с primary key. Номер документа должен быть отдельным полем с уникальностью в нужном scope.

Примеры уникальности:

```sql
UNIQUE (warehouse_id, document_number),
UNIQUE (supplier_id, external_invoice_number),
UNIQUE (batch_id, warehouse_id)
```

Если документные номера формируются по году или типу:

```sql
UNIQUE (document_type, warehouse_id, document_year, document_number)
```

## Constraints

Constraints должны фиксировать инварианты, которые нельзя доверять только application code.

Минимальный набор:

- `NOT NULL` для обязательных доменных полей.
- `FOREIGN KEY` для справочников, партий, складов, документов, резервов и пользователей/actors, если actor представлен локальной таблицей.
- `CHECK` для неотрицательных количеств, допустимых статусов и временных границ.
- `UNIQUE` для идемпотентности, номеров документов, уникальных остатков по партии на складе и дедупликации уведомлений.

Статусы на первом этапе можно хранить как `TEXT` с `CHECK`, чтобы не усложнять миграции enum-типами:

```sql
CHECK (status IN ('draft', 'posted', 'cancelled'))
```

Для доменных связей:

```sql
CHECK (reserved_quantity <= quantity),
CHECK (posted_at IS NULL OR status = 'posted'),
CHECK (reserved_until IS NULL OR reserved_until > created_at)
```

Если нужна уникальность только для активных записей, использовать partial unique index:

```sql
CREATE UNIQUE INDEX ux_unread_low_stock_notification
ON notifications (warehouse_id, item_id, notification_type)
WHERE read_at IS NULL;
```

## Индексы

Индексы проектировать от production-запросов: списки документов, остатки по складу, FEFO, резервы, audit review, outbox worker.

### Остатки и партии

```sql
CREATE UNIQUE INDEX ux_stock_balances_batch_warehouse
ON stock_balances (batch_id, warehouse_id);

CREATE INDEX ix_stock_balances_warehouse_item
ON stock_balances (warehouse_id, item_id);

CREATE INDEX ix_batches_item_expiration
ON batches (item_id, expiration_date);
```

Для FEFO-выдачи нужен быстрый поиск доступных партий:

```sql
CREATE INDEX ix_stock_balances_fefo
ON stock_balances (warehouse_id, item_id, expiration_date, batch_id)
WHERE quantity > reserved_quantity;
```

Если `expiration_date` хранится только в `batches`, FEFO-запрос должен иметь индекс на `batches(item_id, expiration_date, id)` и индекс на `stock_balances(warehouse_id, item_id, batch_id)`.

### Документы и движения

```sql
CREATE INDEX ix_stock_documents_warehouse_status_created
ON stock_documents (warehouse_id, status, created_at DESC);

CREATE INDEX ix_stock_documents_posted_at
ON stock_documents (posted_at DESC)
WHERE posted_at IS NOT NULL;

CREATE INDEX ix_stock_movements_document
ON stock_movements (document_id);

CREATE INDEX ix_stock_movements_batch_warehouse_created
ON stock_movements (batch_id, warehouse_id, created_at DESC);
```

Ledger обычно много читают по периоду:

```sql
CREATE INDEX ix_stock_movements_warehouse_created
ON stock_movements (warehouse_id, created_at DESC);
```

### Резервы

```sql
CREATE INDEX ix_reservations_status_until
ON reservations (status, reserved_until);

CREATE INDEX ix_reservations_actor_status
ON reservations (actor_id, status);

CREATE INDEX ix_reservation_lines_batch_warehouse
ON reservation_lines (batch_id, warehouse_id);
```

### Audit и outbox

```sql
CREATE INDEX ix_audit_log_entity_created
ON audit_log (entity_type, entity_id, created_at DESC);

CREATE INDEX ix_audit_log_actor_created
ON audit_log (actor_id, created_at DESC);

CREATE INDEX ix_outbox_events_status_created
ON outbox_events (status, created_at)
WHERE status IN ('pending', 'failed');
```

Для больших audit/outbox таблиц заранее предусмотреть retention, partitioning по времени или архивирование. На старте можно жить без partitioning, но поля и индексы должны позволять перейти к нему без изменения бизнес-контракта.

## Row Locks и конкурентные изменения

Операции, которые меняют остатки, должны блокировать конкретные строки остатков:

```sql
SELECT *
FROM stock_balances
WHERE batch_id = :batch_id
  AND warehouse_id = :warehouse_id
FOR UPDATE;
```

Для FEFO, где выбирается несколько партий, порядок блокировки должен быть стабильным, чтобы снизить риск deadlock:

```sql
SELECT sb.*
FROM stock_balances sb
JOIN batches b ON b.id = sb.batch_id
WHERE sb.warehouse_id = :warehouse_id
  AND sb.item_id = :item_id
  AND sb.quantity > sb.reserved_quantity
ORDER BY b.expiration_date ASC, sb.batch_id ASC
FOR UPDATE OF sb;
```

Правила:

- Всегда блокировать строки в одном порядке: `warehouse_id`, `item_id`, `expiration_date`, `batch_id`.
- Не держать транзакцию открытой во время внешних HTTP-вызовов, отправки WebSocket, печати документов или тяжелых отчетов.
- Для массовых worker-задач использовать `FOR UPDATE SKIP LOCKED`, чтобы несколько воркеров не брали одну запись.
- Для инвентаризации блокировать склад через отдельную таблицу `inventory_locks` или статус активной `inventory_session`, а затем проверять этот lock во всех write-операциях.

Пример lock-таблицы:

```sql
CREATE TABLE inventory_locks (
    warehouse_id uuid PRIMARY KEY REFERENCES warehouses(id),
    session_id uuid NOT NULL,
    locked_by text NOT NULL,
    locked_at timestamptz NOT NULL DEFAULT now()
);
```

## Audit Hardening

Audit log должен быть пригоден для расследования, а не только для UI-истории.

Рекомендуемые поля:

- `id uuid PRIMARY KEY`;
- `created_at timestamptz NOT NULL DEFAULT now()`;
- `actor_id text NOT NULL`;
- `actor_display_name text`;
- `request_id text`;
- `action text NOT NULL`;
- `entity_type text NOT NULL`;
- `entity_id text NOT NULL`;
- `warehouse_id uuid`;
- `before_json jsonb`;
- `after_json jsonb`;
- `diff_json jsonb`;
- `ip_address inet`;
- `user_agent text`.

Hardening:

- Штатный backend не должен обновлять или удалять audit-записи.
- Доступ на `UPDATE`/`DELETE` к `audit_log` ограничить на уровне DB role.
- Для критичных операций писать audit в той же транзакции, что и доменное изменение.
- Для forbidden attempts и security-sensitive событий писать audit даже без доменного изменения.
- Для долгого хранения рассмотреть monthly partitioning и отдельную роль/процедуру архивирования.

Если нужна дополнительная защита от незаметного изменения записей, можно хранить hash chain:

```sql
prev_hash text,
record_hash text NOT NULL
```

`record_hash` считать от стабильного набора полей и `prev_hash`. Это не заменяет backup/WORM-политику, но помогает обнаруживать ручные изменения.

## Outbox

Outbox нужен для надежной доставки событий после commit: WebSocket, уведомления, интеграции, фоновые jobs.

Рекомендуемая схема:

```sql
CREATE TABLE outbox_events (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    event_type text NOT NULL,
    aggregate_type text NOT NULL,
    aggregate_id text NOT NULL,
    warehouse_id uuid,
    payload jsonb NOT NULL,
    status text NOT NULL DEFAULT 'pending',
    attempts integer NOT NULL DEFAULT 0,
    created_at timestamptz NOT NULL DEFAULT now(),
    available_at timestamptz NOT NULL DEFAULT now(),
    published_at timestamptz,
    last_error text,
    CHECK (status IN ('pending', 'processing', 'published', 'failed')),
    CHECK (attempts >= 0)
);
```

Worker забирает события батчами:

```sql
SELECT id
FROM outbox_events
WHERE status IN ('pending', 'failed')
  AND available_at <= now()
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT :batch_size;
```

Правила:

- Событие создается в той же транзакции, что и изменение остатков/документа.
- Доставка at-least-once: потребители должны выдерживать дубликаты.
- Payload содержит минимум данных, достаточный для сигнала; актуальное состояние клиент дозагружает через API.
- После успешной публикации ставить `status = 'published'`, `published_at = now()`.
- При ошибке увеличивать `attempts`, писать `last_error`, переносить `available_at` с backoff.

## Idempotency

Idempotency keys нужны для POST/PUT/PATCH операций, где повтор запроса может создать дубликаты: проведение документа, резервирование, списание, перемещение, возврат, инвентаризация.

Рекомендуемая схема:

```sql
CREATE TABLE idempotency_keys (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    key text NOT NULL,
    actor_id text NOT NULL,
    method text NOT NULL,
    path text NOT NULL,
    request_hash text NOT NULL,
    status text NOT NULL DEFAULT 'processing',
    response_status integer,
    response_body jsonb,
    resource_type text,
    resource_id text,
    created_at timestamptz NOT NULL DEFAULT now(),
    locked_at timestamptz,
    expires_at timestamptz,
    CHECK (status IN ('processing', 'succeeded', 'failed'))
);

CREATE UNIQUE INDEX ux_idempotency_actor_key
ON idempotency_keys (actor_id, key);

CREATE INDEX ix_idempotency_expires
ON idempotency_keys (expires_at);
```

Поведение:

- Первый запрос создает запись `processing` и блокирует ее в транзакции.
- Повтор с тем же `key`, `actor_id`, `method`, `path` и тем же `request_hash` возвращает сохраненный response, если статус `succeeded`.
- Повтор с тем же ключом, но другим body дает `409 Conflict`.
- Если первый запрос еще `processing`, повтор должен ждать lock, вернуть `409/425` или использовать короткий retry protocol. Выбрать один вариант и зафиксировать в API contract.
- Срок хранения ключей ограничить, например 24-72 часа, затем удалять background job.

## Migration Strategy from SQLite

Миграция должна сохранить текущие бизнес-инварианты, а не просто перенести таблицы.

### 1. Зафиксировать контракт

- Считать текущие тесты acceptance contract.
- Добавить PostgreSQL integration smoke tests для операций с остатками, документами, резервами, инвентаризацией и audit.
- Зафиксировать список таблиц, колонок, статусов и допустимых переходов.

### 2. Спроектировать PostgreSQL-схему

- Создать SQLAlchemy models с PostgreSQL-типами: `NUMERIC`, `timestamptz`, `jsonb`, `uuid`.
- Создать Alembic baseline migration.
- Добавить constraints и индексы сразу в первую production-схему, а не как "потом".
- Для статусов начать с `TEXT CHECK`, если enum lifecycle еще меняется.

### 3. Подготовить данные SQLite

- Проверить отрицательные остатки, резервы больше остатка, дубли партий на складе, битые foreign keys, пустые обязательные поля.
- Нормализовать timestamps: все значения привести к UTC или явно интерпретировать локальную timezone до загрузки в PostgreSQL.
- Проверить decimal precision: строки/числа SQLite преобразовать в `Decimal`, округлить до нужного scale и отдельно залогировать потери точности.
- Проверить `json` поля: валидность JSON, отсутствие секретов, соответствие ожидаемым ключам.

### 4. Загрузить в PostgreSQL

- Загружать справочники, затем партии, остатки, документы, строки документов, движения, резервы, inventory, audit.
- На время bulk load можно отложить некоторые внешние ключи как `DEFERRABLE INITIALLY DEFERRED`, если порядок данных сложный.
- После загрузки выполнить reconciliation: сумма ledger против `stock_balances`, резервы против свободного остатка, документы против движений.
- Создать отчет миграции: количество строк по таблицам, найденные исправления, checksum/агрегаты по остаткам.

### 5. Переключить приложение

- Сначала прогнать staging на production-like копии данных.
- Выполнить миграцию в maintenance window или через dual-run, если простой недопустим.
- На cutover остановить write traffic, выгрузить финальный SQLite snapshot, загрузить PostgreSQL, выполнить reconciliation, переключить connection string.
- После запуска включить усиленный мониторинг: deadlocks, lock wait, slow queries, ошибки constraints, outbox lag, расхождения остатков.

### 6. После cutover

- SQLite оставить только для local development/tests, если это все еще нужно.
- Production backup/PITR проверить реальным restore test.
- Для новых миграций использовать expand-contract: сначала добавить совместимую схему, затем код, затем backfill, затем удалить старое.

## Минимальный production checklist

- Все количества и цены используют `NUMERIC`, не float.
- Все timestamps с временем используют `timestamptz`; сроки годности без времени используют `DATE`.
- Основные payload хранятся в `jsonb`, но ключевые поля вынесены в обычные колонки.
- На остатках есть `UNIQUE (batch_id, warehouse_id)` и constraints на неотрицательные количества.
- FEFO, документы, ledger, резервы, audit и outbox имеют индексы под реальные запросы.
- Все изменения остатков используют row locks или атомарные conditional updates.
- Audit log защищен от штатного update/delete и пишет actor/request context.
- Outbox пишется в одной транзакции с доменным изменением.
- Idempotency покрывает повторные write-запросы.
- Alembic миграции проверяются на пустой базе и на копии данных.
